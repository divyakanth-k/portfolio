Deploying a Real Project on Local Kubernetes

Back to Logs

Most Kubernetes tutorials drop you into a pre-built cluster and hand you a kubectl apply command. This one does not. We build a real web app, containerise it, work through the local-registry gotcha that trips up almost everyone on Docker Desktop, and end up with two healthy pods serving traffic — all on your own machine.

1. What we're building

A task management dashboard called K8s TaskBoard — a dark-themed single-page app served by nginx:alpine. The goal is not the app itself; the goal is to experience the full lifecycle: write code → build image → push to registry → deploy to Kubernetes → observe rolling updates.

The project structure looks like this:

text 
k8s-taskboard/
├── app/                 ← HTML, CSS, JS
├── k8s/
│   ├── deployment.yaml  ← replicas, probes, rolling update
│   ├── service.yaml     ← NodePort exposure
│   ├── configmap.yaml   ← externalised config
│   └── hpa.yaml         ← horizontal pod autoscaler
├── Dockerfile
├── nginx.conf           ← /health endpoint for probes
└── deploy.sh

2. The Dockerfile

The image is tiny — nginx:alpine is under 25 MB. We wipe the default nginx page, copy our static files in, and expose port 80.

dockerfile 
FROM nginx:alpine
WORKDIR /usr/share/nginx/html
RUN rm -rf ./*
COPY ./app/ .
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

The custom nginx.conf adds one important thing — a /health endpoint that returns 200 OK. Kubernetes liveness and readiness probes hit this route, not your app's main page.

nginx 
location /health {
    access_log off;
    return 200 "healthy\n";
    add_header Content-Type text/plain;
}

3. Kubernetes manifests

3.1 Deployment

The Deployment is the brain of the operation. It declares how many pods to run, which image to use, resource ceilings, and the rolling-update strategy.

yaml 
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # spin up one extra pod before killing the old one
      maxUnavailable: 0  # never drop below 2 healthy pods
  template:
    spec:
      containers:
        - name: k8s-taskboard
          image: local-registry:5000/k8s-taskboard:latest
          resources:
            requests: { memory: "64Mi", cpu: "50m" }
            limits:   { memory: "128Mi", cpu: "200m" }
          readinessProbe:
            httpGet: { path: /health, port: 80 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet: { path: /health, port: 80 }
            initialDelaySeconds: 15
            periodSeconds: 20

3.2 Service

Pods are ephemeral — their IPs change every restart. A Service gives them a stable address. We use NodePort so the app is reachable from outside the cluster on port 30080.

yaml 
spec:
  type: NodePort
  selector:
    app: k8s-taskboard   # routes traffic to pods with this label
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080

4. The local-registry gotcha

Here is where most beginners get burned. Docker Desktop's Kubernetes engine runs on kind with containerd as the runtime — not the Docker daemon you use on your Mac. This means images you build with docker build are invisible to your cluster.

You can confirm this with:

bash 
kubectl describe node desktop-control-plane | grep "Container Runtime"
# → ContainerRuntime: containerd://2.x.x
# → ProviderID: kind://docker/desktop/desktop-control-plane

The fix is a local registry container that sits on the same Docker network as the kind node:

bash 
# 1. Start a registry accessible on localhost:5001 from your Mac
docker run -d --restart=always -p 5001:5000 --name local-registry registry:2

# 2. Connect it to the kind network so the cluster node can reach it by hostname
docker network connect kind local-registry

# 3. Push your image via localhost (Mac side)
docker tag k8s-taskboard:latest localhost:5001/k8s-taskboard:latest
docker push localhost:5001/k8s-taskboard:latest

# 4. The cluster node pulls it via the hostname (kind network side)
#    image: local-registry:5000/k8s-taskboard:latest  ← use this in deployment.yaml

# 5. Verify reachability from inside the node
docker exec desktop-control-plane curl -s http://local-registry:5000/v2/k8s-taskboard/tags/list
# → {"name":"k8s-taskboard","tags":["latest"]}
You push via localhost:5001 (Mac port mapping) and the cluster pulls via local-registry:5000 (hostname on the kind Docker network). Two different addresses, same registry container.

5. Deploy and observe

bash 
kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml

# Watch pods come up
kubectl get pods -l app=k8s-taskboard -w

# Wait for the rollout to complete
kubectl rollout status deployment/k8s-taskboard

Once both pods show 1/1 Running, forward a local port to the service:

bash 
kubectl port-forward service/k8s-taskboard-service 9090:80
# Open http://localhost:9090

6. Rolling updates — zero downtime

Make a change to the app. Rebuild and push the image, then trigger a rollout. Kubernetes will create a new pod, wait for its readiness probe to pass, then terminate the old one — traffic is never interrupted.

bash 
docker build -t k8s-taskboard:latest .
docker push localhost:5001/k8s-taskboard:latest

kubectl rollout restart deployment/k8s-taskboard
kubectl rollout status deployment/k8s-taskboard
# → Waiting for deployment "k8s-taskboard" rollout to finish: 1 old replicas are pending termination...
# → deployment "k8s-taskboard" successfully rolled out

7. Useful kubectl one-liners

bash 
# Shell into a running pod
kubectl exec -it <pod-name> -- sh

# Stream logs from all pods with the label
kubectl logs -f -l app=k8s-taskboard

# Scale manually
kubectl scale deployment k8s-taskboard --replicas=4

# Rollback to the previous revision
kubectl rollout undo deployment/k8s-taskboard

# See all resources for the app
kubectl get all -l app=k8s-taskboard

From local to production

The YAML is identical between local and cloud. The only things that change: local-registry:5000/... becomes an ECR or Docker Hub image URL, and NodePort becomes LoadBalancer — which on AWS automatically provisions an ELB. Everything else — Deployments, probes, ConfigMaps, HPA — ports over without a single edit.

That is the real lesson here. Kubernetes abstracts the infrastructure. The cluster can be your laptop or a thousand-node fleet in us-east-1; your manifests stay the same.
