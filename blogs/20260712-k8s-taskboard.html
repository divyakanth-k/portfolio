K8s TaskBoard: Deploying a Real App on Local Kubernetes

Back to Blogs

Most Kubernetes tutorials hand you a kubectl apply and call it done. This one doesn't. We build a real task-management dashboard called K8s TaskBoard, containerise it with Docker, navigate the local-registry gotcha that trips up almost everyone on Docker Desktop, and end up with two healthy pods serving live traffic — all on your own machine.

1. Project structure

The app is a dark-themed single-page dashboard served by nginx:alpine. Alongside the source code sit four Kubernetes manifests that mirror what a real production deployment looks like.

text 
k8s-taskboard/
├── app/
│   ├── index.html       ← dashboard UI
│   ├── style.css        ← dark theme
│   └── app.js           ← task logic
├── k8s/
│   ├── deployment.yaml  ← replicas, rolling update, health probes
│   ├── service.yaml     ← NodePort exposure on :30080
│   ├── configmap.yaml   ← externalised app config
│   └── hpa.yaml         ← horizontal pod autoscaler
├── Dockerfile
├── nginx.conf           ← /health endpoint for Kubernetes probes
└── deploy.sh            ← one-shot build + deploy script

2. The Dockerfile

nginx:alpine is the base — the final image is under 25 MB. We wipe the default nginx welcome page, copy the app in, and drop in a custom nginx.conf.

dockerfile 
FROM nginx:alpine
WORKDIR /usr/share/nginx/html
RUN rm -rf ./*
COPY ./app/ .
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

The nginx config adds a /health route that returns 200 OK. Kubernetes liveness and readiness probes hit this endpoint — not your app's main page — so a slow JS bundle never causes a false failure.

nginx 
location /health {
    access_log off;
    return 200 "healthy\n";
    add_header Content-Type text/plain;
}

3. Kubernetes manifests

3.1 Deployment — replicas, rolling updates, probes

The Deployment is the brain. It declares how many pods to keep alive, enforces resource budgets, and describes exactly how pods should be updated without taking the service down.

yaml 
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # create 1 extra pod before killing the old one
      maxUnavailable: 0  # never drop below the desired replica count
  template:
    spec:
      containers:
        - name: k8s-taskboard
          image: local-registry:5000/k8s-taskboard:latest
          resources:
            requests: { memory: "64Mi",  cpu: "50m"  }
            limits:   { memory: "128Mi", cpu: "200m" }
          readinessProbe:        # when is the pod ready for traffic?
            httpGet: { path: /health, port: 80 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:         # is the pod still alive?
            httpGet: { path: /health, port: 80 }
            initialDelaySeconds: 15
            periodSeconds: 20

3.2 Service — stable network endpoint

Pod IPs change every time a pod restarts, scales, or updates. A Service gives them a permanent address. NodePort exposes it outside the cluster so a browser can reach it directly.

yaml 
spec:
  type: NodePort
  selector:
    app: k8s-taskboard   # send traffic to pods with this label
  ports:
    - port: 80           # Service port (inside cluster)
      targetPort: 80     # container port
      nodePort: 30080    # exposed on the host at localhost:30080

3.3 ConfigMap and HPA

A ConfigMap externalises environment-specific settings — app name, log level, feature flags — so you can change them without rebuilding the image. The HorizontalPodAutoscaler watches CPU and memory metrics and scales the replica count up or down automatically.

4. The local-registry gotcha

This is where most people hit a wall. Docker Desktop's Kubernetes runs on kind with containerd as its runtime — entirely separate from the Docker daemon you use on your Mac. Images built with docker build exist in Docker's layer cache, not in containerd's, so the cluster simply can't see them.

bash 
# Confirm your cluster is running on kind / containerd
kubectl describe node desktop-control-plane | grep "Container Runtime"
# ContainerRuntime: containerd://2.x.x
# ProviderID:       kind://docker/desktop/desktop-control-plane

The fix: run a registry:2 container, connect it to the kind Docker network, and push images through it. The Mac side pushes via localhost:5001; the cluster node pulls via the container hostname local-registry:5000.

bash 
# 1. Start the registry, exposed on your Mac at port 5001
docker run -d --restart=always -p 5001:5000 --name local-registry registry:2

# 2. Join it to the kind network so the cluster node can resolve it by name
docker network connect kind local-registry

# 3. Build, tag, and push via localhost (Mac Docker daemon)
docker build -t k8s-taskboard:latest .
docker tag k8s-taskboard:latest localhost:5001/k8s-taskboard:latest
docker push localhost:5001/k8s-taskboard:latest

# 4. Confirm the node can reach it
docker exec desktop-control-plane \
  curl -s http://local-registry:5000/v2/k8s-taskboard/tags/list
# → {"name":"k8s-taskboard","tags":["latest"]}
Push via localhost:5001 (Mac port mapping). Pull via local-registry:5000 (kind Docker network hostname). Same registry container, two different addresses.

5. Deploy and verify

bash 
# Apply manifests in dependency order
kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml

# Watch pods start up
kubectl get pods -l app=k8s-taskboard -w

# Block until the rollout is done
kubectl rollout status deployment/k8s-taskboard
# → deployment "k8s-taskboard" successfully rolled out

# Forward a local port (NodePort doesn't bind on Docker Desktop)
kubectl port-forward service/k8s-taskboard-service 9090:80
# Open → http://localhost:9090

When both pods show 1/1 Running and the rollout reports success, the app is live. The dashboard displays real-time pod names, replica counts, and service details pulled from the Kubernetes deployment info section at the bottom of the page.

6. Rolling updates with zero downtime

Change something in the app. Rebuild, push, and trigger a restart. Kubernetes spins up a new pod, waits for its readiness probe to pass, then drains and terminates the old one. Traffic flows the entire time.

bash 
docker build -t k8s-taskboard:latest .
docker push localhost:5001/k8s-taskboard:latest

kubectl rollout restart deployment/k8s-taskboard
kubectl rollout status deployment/k8s-taskboard
# Waiting for deployment "k8s-taskboard" rollout to finish:
#   1 old replicas are pending termination...
# deployment "k8s-taskboard" successfully rolled out

7. Handy kubectl commands

bash 
# Open a shell inside a running pod
kubectl exec -it <pod-name> -- sh

# Stream logs from all matching pods at once
kubectl logs -f -l app=k8s-taskboard

# Scale to 4 replicas manually
kubectl scale deployment k8s-taskboard --replicas=4

# Roll back to the previous revision
kubectl rollout undo deployment/k8s-taskboard

# Show every resource owned by this app
kubectl get all -l app=k8s-taskboard

# Clean up everything
kubectl delete -f k8s/

Local vs. production

The YAML files are identical between local and cloud. Two things change when you move to AWS EKS, GKE, or Azure AKS:

  • local-registry:5000/k8s-taskboard:latest becomes an ECR or Docker Hub image URL pushed by your CI pipeline.
  • type: NodePort becomes type: LoadBalancer — the cloud provider automatically provisions an external load balancer.

Deployments, probes, ConfigMaps, resource limits, and the HPA carry over untouched. Kubernetes abstracts the infrastructure — the same manifests describe a single-node laptop cluster and a thousand-node production fleet.
